# StackAlign

A standalone Bash-based LEMP installer and manager for supported EL-family Linux systems on x86_64.

## Project status

**Design documents complete for M0/M1/M2a scope; implementation pending.** This repository contains reviewed design documentation only. It does not yet contain the installer, configuration parser, workload tuner, tenant isolation implementation, or runtime deployment workflows. A design discussed or drafted in a conversation is not repository implementation.

## Scope

StackAlign manages LEMP servers and supported self-hosted PHP application workloads. Hosted SaaS services are outside server-side tuning scope. Unrelated application domains and services are intentionally excluded.

Planned workloads include generic PHP, WordPress/WooCommerce, Laravel, and selected self-hosted applications. X-Cart 5.6 is a guarded LEMP workload profile. Its 2 GiB policy floor is advisory: below-floor conditions produce warnings and prominent doctor-report findings. **Arithmetic refusal because no candidate fits is the only hard sizing refusal.** A policy warning alone must not prevent an otherwise feasible plan.

A slave_web role is a web-only node behind an upstream load balancer or DNS rotation. It does not host local MariaDB by default; local service costs are supplied as tuner inputs rather than assumed by the algorithm. See [the slave-web design](docs/research/slave-web-node.md).

## Operating principles

- Bash is the installer/runtime language. Python may be used for development tests and benchmarks only.
- Target EL-family x86_64 systems; supported distributions and versions must be pinned and tested explicitly.
- No unattended update application.
- No secrets in the repository, logs, snapshots, or Git history. Runtime secrets belong under /etc/stackalign/secrets/ with restrictive permissions; snapshots exclude them by default.
- No network bootstrap, telemetry, or hidden remote configuration.
- No unmeasured performance, memory, or recovery-time claims.
- All sizing formulas and sizing tables belong only in docs/TUNING.md. A sizing table must be generated by executing the implementation against documented cases and pasting actual output; hand-computed replacement tables are prohibited.
- Clearly distinguish implemented, tested, untested, and blocked work.

## Development workflow

Work on short-lived feature branches, review changes through pull requests, and preserve main. Do not force-push. A merge is not evidence of a successful build, installation, or runtime validation.
